# Premium books: detail

Moved verbatim from `GEMINI.md` on 2026-11-15, when the always-loaded instruction files were compacted under the 150k-character limit. `GEMINI.md` keeps the binding summary of each rule and points here; each heading below names the `GEMINI.md` section the text belongs to. Read this file before the work its pointer in `GEMINI.md` names. In the moved text, "this section" and "this file" mean the `GEMINI.md` section named in the heading.

## From section 30 (Premium Books (Added 2026-11-01))

- **Public surfaces:** the D1 seeder (`scripts/migrate-to-d1.ts`) writes the row of a premium book with its title and subject label and an empty `content_md`, so the text never reaches `db/seed.sql` or `dawnbook-db`. Since 2026-11-27 (owner decision) a premium book is unlisted, hidden from the hub: the home page renders no card for it, `sitemap.xml` and `llms.txt` carry none of its URLs (root included, and `check-seo.ts` fails a listed one), `GET /api/books` leaves it out for non-admin callers, `GET /api/stats` leaves it out of every D1 figure, and `scripts/announce-new-books.ts` skips it after a deploy (`--slug` still announces it). It is reached by a direct link only and stays indexable. For a free book, `llms.txt` lists the book root and chapters 2 onward without `.html`; both files leave chapter 1 (the first `SUMMARY.md` entry in `manifest.json`) out because its canonical is the book root (section 31). `manifest.json` still carries every built slug in `books` and the built premium slugs in `premium`, which the deploy guard, `inject-gating.ts`, the sitemap and the announcement read.
- **Verbatim proof:** `bun run scripts/premium/verbatim-proof.ts --pdf <original.pdf> --book <dawnbook-premium>/books/<slug>` compares the PDF text with the chapters in `SUMMARY.md` order, token by token, and exits 0 only when the only differences are page numbers, running headers and footers, and bullet glyphs (all listed with `--report`). Run it after any edit to a verbatim premium book (no edition in the registry) or to the pipeline. It does not apply to a revised edition (`"edition": 2026`), whose text differs from the PDF by design.
- **Sign-in through belajarcarabelajar.com (added 2026-11-01):** buyers whose purchase email is not a Google account sign in through the store. The sign-in page and the premium 403 page offer "Masuk lewat akun belajarcarabelajar.com", a link to Dawnbook `/api/auth/bcb/start?next=<path>`, which sends the reader on to `https://belajarcarabelajar.com/masuk-dawnbook?next=<path>&s=<state>`. That route lives in the bcb repository and requires the store session (email code or Google); it answers 303 to `/api/auth/bcb?t=<token>&next=<path>&s=<state>` on Dawnbook, which sets the session cookie and redirects to the safe `next`. Against login CSRF the links go through the same-origin `/api/auth/bcb/start?next=<path>`, which stores 32 random bytes (43 base64url characters) in the `__Host-bcb_sso_state` cookie (`Path=/`, no Domain, 10 minutes, HttpOnly, Secure, SameSite=Lax; the `__Host-` prefix stops a sibling subdomain from planting it, and a cookie under the old unprefixed name is ignored) and passes the same value to the store as `s`, which the store must return as `s` on `/api/auth/bcb`; the hand-off answers `sso_invalid` unless cookie and `s` match, checked before the token is read or its nonce used, and clears the cookie on every response, so a link carrying someone else's token cannot sign a visitor in to that account.
  - **Token:** `base64url(email).exp.nonce.signature`, where the signature is HMAC-SHA256 over `dawnbook-sso|<email>|<exp>|<nonce>` with the shared secret (`functions/lib/bcb-sso.ts`). `exp` is at most 120 seconds ahead, and each token is single use: its nonce is recorded in `rate_limits` as `sso:<nonce>`.
  - **Users:** a new user created by the hand-off gets `google_sub = "bcb:<email>"`. The Google callback (`functions/api/auth/callback.ts`) links such a user on the first Google sign-in with the same email, and refuses an email already owned by another Google account with `account_conflict`.
  - **Secrets (entered by the owner, never by an agent):** `BCB_SSO_SECRET` on the Dawnbook Pages project and `DAWNBOOK_SSO_RAHASIA` in the bcb Worker env `apex`, the same value, at least 32 characters.
  - **Failure modes:** `/sign-in?error=sso_unavailable` when the secret is missing, `/sign-in?error=sso_invalid` for an expired, forged, malformed or reused token. Both fail closed.
  - **Cross-repo contract:** both repositories check the shared fixture `tests/fixtures/sso/token.json`, so a change to the token format must land in both at once.
  - **Revert:** delete the secret on either side (both sides then fail closed), or revert the pull requests.
- **Premium images in R2 (added 2026-11-01):** the images of a premium book are not in the Pages output. They live in the R2 bucket `dawnbook-premium-media` (binding `PREMIUM_MEDIA`) under `books/<slug>/images/<path>`, and the middleware serves `/books/<slug>/images/...` from the bucket after the same access check as the pages. Images under `images/public/` (chapter 1) need no session, and a missing binding answers 503. A free book's images stay on Pages.
  - **Build:** after the mdBook builds, `scripts/build.ts` moves `output/books/<slug>/images/` of every premium slug to `.premium-media/books/<slug>/images/` (gitignored and recreated on every build; `stagePremiumMedia` in `scripts/premium/move-media.ts`).
  - **Sync:** `bun run scripts/premium/sync-media.ts upload|prune [--dry-run]`. `upload` puts every staged file that the bucket lacks or whose MD5 differs from the object's etag (R2 sets a single-part upload's etag to its MD5), with its content type; a file other than svg, png, jpg, jpeg, gif, webp or avif stops the upload before anything is written. `prune` deletes every object under `books/` that is not staged, and refuses to run when the staging folder is missing or empty, so a build without the private books can never wipe the bucket. `--dry-run` prints the plan and writes nothing (it still lists the bucket). Exit 0 done, 1 failure or refusal, 2 usage. `cf` prints no list cursor, so the script pages with `--start-after` until a page comes back empty.
  - **Deploy order:** `scripts/deploy-website.sh` runs `upload` before the Pages deploy (step 3b; a failure aborts the deploy, because the new pages would point at missing images) and `prune` as the last step (7), after the PDF release below.
  - **Before the first deploy and on rollback:** the bucket must exist first (`cf r2 buckets create dawnbook-premium-media`), or step 3b stops the deploy before Pages changes. Keys are not versioned: `upload` overwrites an image in place and `prune` deletes images the new build no longer has. Rolling Pages back to an older deployment therefore needs the matching images uploaded again (build that commit, then `sync-media.ts upload`), or its removed images answer 404.
  - **Local preview:** after `bun run build`, `output/` holds no premium images. To see them in a local preview, copy them back with `cp -r .premium-media/books/. output/books/`. `deploy-website.sh` rebuilds first, so the copy never reaches Pages; never deploy that `output/` by hand.
  - **Revert:** remove the move in `scripts/build.ts`, steps 3b and 7 of `scripts/deploy-website.sh`, `scripts/premium/move-media.ts`, `scripts/premium/sync-media.ts`, the `PREMIUM_MEDIA` binding and the image branch of the middleware. The images then ship with Pages again, behind the same gate as the pages. Delete the bucket only after that deploy.
- **Store PDFs (added 2026-11-01):** `scripts/premium/print-pdf.ts` prints the store PDF through the web build's preparation (the same prepared copy with inlined diagrams and decorations, so the web and the PDF cannot drift) and adds the cover, the watermark, the chapter bookmarks and the copy restriction. The watermark runs along the A4 diagonal from corner to corner and spans 90 % of it (owner, 2026-11-02: the old -30 degree mark was too small); Chromium clips a fixed element to the page area, so the margins get the same sheet-sized image as an `@page` background (`watermarkSvg`, `injectWatermark`). Table cells, and links or code inside them, wrap only between words at 10 pt (owner, 2026-11-02: `overflow-wrap: anywhere` printed "Pen / eliti / an"). Step 6 of every deploy, after the Pages deploy, runs `bun run scripts/premium/release-pdfs.ts`: it reprints each registry book with `"edition": 2026` (a revised book without its `print-cover.svg` fails the run) and overwrites `member/<slug>.pdf` in the store bucket `bcb-admin-media`, keeping no backup copy. It exits non-zero and names the books whose PDF is stale.
  - **After the Pages deploy:** when step 6 or 7 fails, `deploy-website.sh` still runs the other one, then names the failed command and exits 1. The site is already live: fix the cause and re-run that command.
  - **Revert:** remove step 6 from `scripts/deploy-website.sh`; the store keeps the last PDFs it received.
- **Related hardening (2026-11-01):** `getBooks` in `functions/lib/db.ts` returns book text (`content_md`) only for admin callers, even when a caller asks for it. `isPublicPath` in `functions/lib/gating.ts` rejects any path with a `.` or `..` segment, so a decoded `%2F..%2F` cannot climb from a free chapter into a gated one.
- **Revert:** empty the registry (`{"books": {}}`), remove the `LMS_DB` binding and the premium branch of `functions/_middleware.ts`, delete `functions/lib/premium.ts`, `scripts/premium-sync.ts`, `scripts/check-premium-output.ts`, the deploy guard in `scripts/deploy-website.sh`, the gate exemptions for premium slugs, and this section (with the one-line pointers at the end of sections 14, 16, 24 and 29).
